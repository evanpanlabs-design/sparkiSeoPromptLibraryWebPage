## 二、项目介绍 — STAR 法则

### S（Situation）：项目背景

> **当时是什么情况？遇到什么问题？**

**回答**：
> Twitter 上有大量 AI 视频生成爱好者在分享高质量的生成 Prompt，比如 Veo 3、Sora、Runway 的玩家。但这些 Prompt 散落在海量推文里，没有一个集中的平台供创作者检索。我希望做一个工具，能自动把这些 Prompt 采集下来，筛选质量，整理发布。

### T（Task）：我的任务

> **我负责什么？**

**回答**：
> 独立负责整个项目：需求分析、架构设计、编码实现、部署维护。没有团队分工，需要独立完成从爬虫到网站发布的全链路。

### A（Action）：具体行动

> **我做了什么？用了什么技术方案？**

**主题1：评测体系设计（JD 最匹配）**
> 采集下来的推文里，大部分是无效内容——太短、没有指令、或者只是感叹句。
> 我设计了两层过滤：
> - 第一层：关键词 + 长度过滤（至少 15 词，包含"prompt"/"AI video"等关键词）
> - 第二层：LLM 4 维度评分，低于 0.4 直接淘汰
>
> 4 个维度：Specificity（25%）、Visual Detail（30%）、Novelty（20%）、Generatability（25%）。
> 视觉细节权重最高，因为这是生成质量的关键。
> 这套体系本质上就是一个"内容质量评估框架"，设计思路和 AI 产品经理设计评测集是类似的。

**主题2：语义搜索/RAG（匹配 JD 的 RAG/推荐）**
> 每条 Prompt 入库时调用 Gemini embedding API 生成 768 维向量，存到 SQLite BLOB。
> 用户搜索时把 query 也 embedding，和库里向量做余弦相似度排序，返回 top-k。
> 这个方案本质上就是 RAG（检索增强生成）的简化版——先检索相关内容，再利用检索结果。
> 对于本地生活 AI 助手来说，"用户想要什么"和"从库里找什么"这个匹配逻辑是相同的。

**主题3：ReAct Agent 与跨团队协作（匹配 JD 的 Agent / 协调能力）**
> V3 版本我开发了对话式 Agent，用 LangGraph StateGraph 实现 ReAct 架构。
> 6 个 Node：start / think / plan / act / observe / final_reply。
> 每个工具（爬虫、评分、图生成、发布）都是独立的 Skill 注册到 Registry 里，
> LLM 通过 get_tool_schemas() 获取所有工具定义，自己决定调用哪个。
> 这让我理解了怎么设计一个"多模块协作的系统"，各模块各司其职，通过共享状态协作——
> 这和美团需要与微信团队多方协作的逻辑是相通的。

**主题4：工程落地（Python + SQLite）**
> 所有配置进 YAML，不硬编码；脚本支持 --dry-run / --limit 参数；
> 数据库用了 WAL 模式支持多进程并发读；图片生成加了 2 秒间隔的 rate limit 保护。

### R（Result）：成果

> **结果怎么样？**

**回答**：
> 采集了 131 条高质量 Prompt，发布到 GitHub Pages。
> 质量评分过滤掉了约 60% 的低质量内容。
> 图片生成通过 429 重试机制，成功率超过 95%。

## 三、高频问题 & 回答要点

### Q1：你觉得 AI 产品和传统产品有什么区别？

**要点**：
> 传统产品输出是确定的（点击哪个按钮发生什么），AI 产品输出是不确定的（同一个 Prompt 每次结果可能不同）。所以 AI 产品经理需要设计评测体系来衡量效果，需要接受概率性结果，需要定义"好"的标准——这是和传统产品最大的区别。

### Q2：你们怎么评估 Prompt 质量？

**要点**：
> 4 个维度：Specificity（具体性）、Visual Detail（视觉细节）、Novelty（新颖度）、Generatability（可生成性）。各有权重（25/30/20/25%），加权求和，低于 0.4 的过滤掉。这套体系本质上和 AI 产品经理设计评测集是类似的思路。

### Q3：解释一下 RAG 是什么？你的项目里有类似的实现吗？

**要点**：
> RAG = Retrieval-Augmented Generation，检索增强生成。流程是：先从库里检索相关知识，再用 LLM 结合检索结果生成回答。我的项目中，Embedding 搜索就是"检索"这一步——把用户 query 变成向量，去库里找最相似的 Prompt，然后返回给用户。只不过我们没有接 LLM 生成这一步，只有检索。但原理是一样的。

### Q4：ReAct 和 Function Calling 的区别？

**要点**：
> Function Calling 是"用户说啥，LLM 直接调工具"，适合单步操作。ReAct 有显式的 Thought + Observation，LLM 先推理再行动，可以自主规划多步任务链，每一步的 Observation 写入记忆供下一步使用。

### Q5：为什么用 LangGraph 而不是 LangChain？

**要点**：
> LangChain 太重，我们只需要 StateGraph + checkpointer。自己封装更轻量，完全控制代码结构。LangGraph 是 LangChain 的底层核心，概念更直接。

### Q6：遇到最难的问题是什么？怎么解决的？

**要点**（选一个）：
> 1. **WindowsPath bug**：GCS 的 download_to_file() 不能接受 WindowsPath 对象，用 open(path, 'wb') 包装解决
> 2. **X.com SSL proxy**：配置 OPENAI_API_BASE 环境变量绕过代理直连
> 3. **图片路径404**：HTML 模板和实际图片路径不一致，用 --sync-images 脚本复制到扁平目录解决

### Q7：如果让你重来，会怎么改进？

**要点**：
> V1 pipeline 的 phase 耦合太紧，V3 把它们拆成了独立的 Skill。这样每个 phase 可以单独测试和替换，也方便 Agent 精确控制每一步。这也是软件工程里的"高内聚低耦合"原则。

### Q8：你认为本地生活 AI 助手最难解决的问题是什么？

**要点**：
> 我觉得有两个难点：一是**服务闭环**——本地生活最终要完成预订、支付等操作，需要和美团内部系统强耦合，技术边界和产品边界的协调是难点；二是**用户意图理解**——"我想吃附近好吃的"和"给我推荐一个餐厅"是完全不同的意图，需要足够强的意图识别能力。

### Q9：你为什么想做 AI 产品经理？

**要点**：
> 我本身在用 AI 工具做产品开发，对 AI 能力边界有直观感受。我对内容质量和 Prompt 敏感，知道什么是"好"的标准，这在做 AI 产品时很重要。Sparki 项目让我学会了从用户需求出发设计评测体系，这也是产品经理的核心工作。

### Q10：你能为这个岗位带来什么？

**要点**：
> 1. 对 AI 能力边界的直观理解——天天在用 LLM，知道它擅长什么、不擅长什么
> 2. 数据驱动的评测思维——4 维度评分体系是我自己设计的，理解怎么定义评测标准
> 3. 工程落地能力——能独立把 AI 产品从 0 到 1 跑通，不只是画原型
> 4. 跨团队协作经验——项目中协调过 Apify、GCS、GitHub 等多方服务，有协调多方资源的实战经验
